# Prompt Injection and Jailbreak Detection: Working Explanations

## 1. Project Intent
This project builds a binary text classifier that predicts whether an input prompt is:
- `SAFE` (normal user request)
- `INJECTION` (prompt injection or jailbreak attempt)

The model is DistilBERT fine-tuned on a prompt-injection dataset. The repository supports:
- model training
- post-training evaluation
- attention-based interpretability
- inference API usage
- Streamlit dashboard visualization
- optional adversarial data augmentation

## 2. End-to-End Workflow

### Stage A: Data ingestion and preparation
Implemented primarily in `train.py`.

1. Load dataset from HuggingFace (`jayavibhav/prompt-injection`).
2. Normalize into a single DataFrame with columns: `text`, `label`.
3. Perform basic EDA:
   - class distribution
   - token length distribution
   - save chart to `data/eda_overview.png`
4. Split into train/val/test with stratification (80/10/10).
5. Save splits:
   - `data/train.csv`
   - `data/val.csv`
   - `data/test.csv`
6. Tokenize using DistilBERT tokenizer (`max_length=128`).

### Stage B: Training
Implemented in `train.py`.

1. Load `distilbert-base-uncased` classifier head with 2 labels.
2. Compute class weights from train labels.
3. Use custom `WeightedTrainer` to apply class-weighted cross-entropy.
4. Train with HuggingFace `Trainer`.
5. Save model artifacts to `models/distilbert-injection`.

Important training settings in current code:
- epochs: `2`
- batch size: `16`
- learning rate: `2e-5`
- warmup ratio: `0.1`
- mixed precision: `fp16=True`
- early stopping patience: `2`

### Stage C: Evaluation
Implemented in `model_evaluate.py`.

1. Load saved model from `models/distilbert-injection`.
2. Load `data/test.csv`.
3. Run batched inference.
4. Compute and save:
   - classification report to `data/classification_report.txt`
   - confusion matrix and ROC/confidence plots to `data/evaluation_plots.png`

Also prints examples of:
- correctly detected injection samples
- missed injection samples (false negatives)

### Stage D: Attention interpretability
Implemented in `attention_viz.py`.

1. Reload model with `output_attentions=True`.
2. Run a curated set of example prompts.
3. Use last-layer mean-head attention and extract CLS-row attention.
4. Save per-example attention bar charts:
   - `data/attention_heatmap_1.png` ... `data/attention_heatmap_6.png`
5. Aggregate token attention over injection examples and save:
   - `data/attention_top_tokens.png`

### Stage E: Inference API
Implemented in `inference.py`.

The key runtime API is:
- `detect_injection(text: str) -> dict`

Behavior:
1. Lazily loads tokenizer/model once (singleton pattern).
2. Predicts class probabilities.
3. Maps injection probability to risk tiers:
   - LOW: `< 0.30`
   - MEDIUM: `0.30 to < 0.70`
   - HIGH: `>= 0.70`
4. Returns label, confidence, and risk metadata.

Batch mode:
- `detect_batch(texts: list) -> list`

### Stage F: Web app visualization
Implemented in `app.py` with Streamlit.

Dashboard pages:
1. Live Detector
2. EDA Charts
3. Evaluation Results
4. Attention Heatmaps
5. Classification Report
6. Dataset Viewer

The app is a presentation and analysis layer on top of artifacts generated by training/evaluation scripts.

### Stage G: Optional adversarial augmentation
Implemented in `adversarial.py`.

1. Read `data/train.csv`.
2. For injection samples, call Anthropic API to create paraphrased attacks.
3. Save:
   - `data/adversarial_injections.csv`
   - `data/train_augmented.csv` (original + adversarial samples)

This stage is intended to improve robustness to paraphrased jailbreak attempts.

## 5. Inconsistencies Found (Codebase Audit)

1. README path mismatch
- README commands reference `src/train.py`, `src/evaluate.py`, `src/inference.py`, `src/adversarial_augment.py`.
- Actual files are at repository root: `train.py`, `model_evaluate.py`, `inference.py`, `adversarial.py`.

2. README structure mismatch
- README describes folders `src/` and `notebooks/`.
- Current repository has scripts and notebooks at root.

3. README model artifact mismatch
- README mentions `pytorch_model.bin`.
- Current model directory stores `model.safetensors`.

4. Training hardware claim mismatch
- README says CPU training is possible (slower).
- `train.py` hard-fails when CUDA is unavailable:
  - raises `RuntimeError` if no GPU.

5. Epoch mismatch
- README training section describes up to 4 epochs / early stopping context.
- Current `train.py` sets `NUM_EPOCHS = 2`.

6. Notebook 01 unresolved imports
- `01_eda.ipynb` imports from `eda` module (`load_data`, `normalise_columns`, etc.).
- No `eda.py` exists in this repository.

7. Notebook 02 unresolved imports and API mismatch
- `02_training.ipynb` imports `build_datasets` from `preprocess` (missing file).
- Also calls `from train import train`, but `train.py` is script-style and does not expose a `train()` function returning `(trainer, tokenised_ds)`.

8. Notebook 03 unresolved imports and function mismatch
- `03_evaluation.ipynb` expects `run_evaluation` in `evaluate` module.
- Actual file is `model_evaluate.py` and it does not expose `run_evaluation()`.
- Notebook expects `attention_viz.load_model_with_attentions` and `attention_viz.plot_comparison`, which do not exist in current `attention_viz.py`.

9. `adversarial.py` base path likely incorrect
- `BASE = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))`
- Since `adversarial.py` is already at repository root, this resolves one level above project root.
- Result: `DATA_DIR` may point outside project (`../data`) instead of project `data/`.

10. Minor code quality mismatch
- `app.py` imports `Image` from PIL but does not use it.

## 6. Actual Execution Order (Current Repository)
Use this sequence for reproducible operation with the present code:

1. Install dependencies from `requirements.txt`.
2. Train model:
   - `python train.py`
3. Run evaluation:
   - `python model_evaluate.py`
4. Generate attention visualizations:
   - `python attention_viz.py`
5. Launch web dashboard:
   - `streamlit run app.py`
6. Optional API usage:
   - import `detect_injection` from `inference.py`
7. Optional adversarial dataset creation:
   - `python adversarial.py --n_per_example 3 --max_examples 50`

## 7. Runtime Data Contracts

### Input contract
- model expects plain text string prompts
- labels in CSV expected as numeric:
  - `0` -> SAFE
  - `1` -> INJECTION

### Output contract from inference
`detect_injection` returns:
- `label`
- `confidence`
- `risk_level`
- `safe_prob`
- `inject_prob`

This is suitable as a pre-filter for external LLM applications.
